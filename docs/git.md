# Памятка по работе с репозиторием

## Один раз в начале семестра

Представьтесь git — эти данные попадут в каждый ваш коммит:

```bash
git config --global user.name "Иванов Иван"
git config --global user.email "ваша-почта@example.com"
```

Склонируйте свой репозиторий (ссылка — на странице репозитория, кнопка
**Code**):

```bash
git clone https://github.com/ОРГАНИЗАЦИЯ/bookshelf-ivanov.git
cd bookshelf-ivanov
```

## Каждая лабораторная работа

**1. Обновиться и отвести ветку.** Обязательно от свежего `main`:

```bash
git switch main
git pull
git switch -c lab-04
```

**2. Работать, сохраняя промежуточные результаты.** Не копите всё в один
коммит — делайте коммит после каждого законченного куска:

```bash
git add .
git commit -m "ЛР №4: класс LibraryStorage, сохранение в JSON"
```

**3. Отправить ветку на GitHub:**

```bash
git push -u origin lab-04
```

Первый раз для ветки — с ключом `-u`, дальше достаточно `git push`.

**4. Открыть pull request.** Зайдите на страницу репозитория — GitHub сам
предложит кнопку **Compare & pull request**. Заголовок: `ЛР №4. Работа с
текстовыми файлами`. Заполните шаблон и нажмите **Create pull request**.

**5. Доработать по замечаниям.** Если преподаватель поставил
**Changes requested** — исправляйте в той же ветке:

```bash
git add .
git commit -m "ЛР №4: обработка повреждённого файла"
git push
```

PR обновится сам. Новый открывать не нужно.

## Если правите файл прямо на GitHub

Иногда удобно поправить мелочь через веб-интерфейс, кнопкой с карандашом.
Тогда внизу страницы GitHub предложит «Create a new branch for this commit
and start a pull request» и **подставит своё имя ветки** вида
`ваш-логин-patch-1`.

Имя нужно заменить на `lab-NN` вручную, прямо в этом поле. Иначе работа не
попадёт в сводку успеваемости, и преподавателю придётся разбираться, к какой
лабораторной относится ваш pull request.

Заголовок PR тоже подставляется автоматически («Update README.md») — его
нужно заменить на `ЛР №N. Тема работы`.

## Частые вопросы

**Запушил в `main`, получил отказ.**
Так и задумано, ветка защищена. Перенесите работу в отдельную ветку:

```bash
git switch -c lab-04
git push -u origin lab-04
```

**Забыл отвести ветку и работал прямо в `main` (локально).**
Ничего страшного, коммиты ещё не отправлены:

```bash
git switch -c lab-04     # ветка создастся прямо здесь, со всеми коммитами
git push -u origin lab-04
```

**При `git pull` появились конфликты.**
Значит, ветка отводилась от устаревшего `main`. Обновите ветку:

```bash
git switch lab-04
git fetch origin
git merge origin/main
```

Git отметит конфликтующие места в файлах символами `<<<<<<<`, `=======`,
`>>>>>>>`. Оставьте нужный вариант, удалите маркеры, затем:

```bash
git add .
git commit
git push
```

**Случайно закоммитил `build/` или `.dart_tool/`.**
Эти каталоги перечислены в `.gitignore`, но если попали в индекс раньше:

```bash
git rm -r --cached build .dart_tool
git commit -m "Убрать служебные каталоги из репозитория"
```

**Что писать в сообщении коммита.**
Что сделано, а не что происходило. Хорошо: «ЛР №4: экспорт каталога в CSV».
Плохо: «фикс», «работает», «ура».

## Чего делать не нужно

- Не коммитить `build/`, `.dart_tool/`, `.idea/` — они в `.gitignore`.
- Не делать `git push --force` в `main`.
- Не открывать новый PR на ту же работу — правьте существующую ветку.
- Не копировать код у однокурсников: история коммитов и ревью это показывают.
